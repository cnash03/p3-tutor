Context and memory in an agent

By the end of this lesson you can say what is in the model's context at each step of your makerspace assistant, what survives from one step to the next and from one visit to the next, and which of three tools (the context itself, saved notes, retrieval) should hold each piece of information.

Why this matters for you

Your assistant must answer from long machine manuals and remember each student's training status between visits, all on a small budget. Those are three decisions about what goes where, and you will have to defend them at your design review. This lesson gives you the vocabulary and the rules of thumb to do that.

Today's twist is in the phrase "sends the result back to the model": what exactly is sent, and what happens to it afterwards?

The context window: what the model sees 6 min

Start with a concrete case. A student types: "How do I change the lens on the laser cutter?" Before the model writes a single word, the program has to assemble everything the model will be allowed to read. For your assistant that is:

  • the system prompt: your standing instructions ("You are the makerspace assistant. Never book a machine without checking training.");
  • the tool descriptions: the name, purpose and parameters of check_calendar, search_manuals and the rest;
  • the conversation so far: the student's messages and the assistant's earlier replies;
  • any tool results that have come back, such as manual pages.

All of that, plus the reply the model is about to write, is the context: the set of tokens the model is given when it generates text (Anthropic, Effective context engineering for AI agents). A token is a small piece of text, often a short word or part of a word. The context window is the limit on how many tokens the model can take into account in one call. Everything must fit inside it, and nothing outside it exists for the model.

Two consequences matter for your project.

First, the window is a budget in two senses. It has a hard size limit, and every token in it is something you pay for on each call. Models are billed by tokens read and written, so a bloated context is a more expensive request.

Second, a fuller window is not a better window. Anthropic's engineers describe context rot: as the number of tokens in the context grows, the model's ability to accurately recall information from it decreases. They treat context as a finite resource with diminishing returns, and say the aim is the smallest set of high-signal tokens that gets the result you want (same source). Think of a desk: a student who needs one page of the laser manual is better served by that page than by a desk buried under the whole shelf.

Everyday analogy: your working memory when you do a circuit problem. You hold the numbers you need right now, not every number from the course. The context window plays that role for the model. It is an analogy, not a claim about how models work inside.

Between steps: the context grows 7 min

Here is the idea that surprises most people. The model keeps nothing from one call to the next. Each call starts blank. What looks like the model "remembering" the calendar result is the program sending it again, inside the input, on every call. In the loop you already know, this is what "the result goes back to the model" really means: the program appends the model's request and the tool's result to the context, and sends the whole thing again.

Follow one request through, with made-up but plausible sizes. The student asks: "Is the laser cutter free tomorrow at 3 pm, and what do I need to do first?" The system prompt and tool descriptions take about 2,000 tokens, and the question about 50.

Model callWhat is added before itInput size (tokens)
1System prompt, tools, question2,050
2Model's request (50) + calendar result (300)2,400

4Model's request (50) + training record (200)4,200

Add the last column: 2,050 + 2,400 + 3,950 + 4,200 = 12,600 input tokens for one answer, three times the final context of 4,200. The system prompt is read four times, and the manual pages are read twice even though they were used once. This repeated reading is why a long agent run costs more than the length of its final context suggests, and why cost per request is a design concern for you. (Providers offer ways to discount re-read text, such as prompt caching, but the model still reads it each call; check your provider's current pricing rather than assuming a number.)

A common mix-up

"The model remembers what happened earlier in the run, the way I do." It is tempting because the assistant's answers sound continuous. In fact the model has no state between calls; the program holds the history and re-sends it. This matters because it puts you in charge: whatever you leave out of the next call, the model has lost.

What to do when the context fills up

A growing context needs management. Anthropic describes three techniques for long runs (source):

  • Compaction: when the conversation nears the limit, summarise it and start a new context window containing the summary.
  • Structured note-taking: the agent writes notes to storage outside the context window and reads them back later. We return to this in the next section.
  • Sub-agents: a helper works on a focused task in its own clean context and returns only a short summary. This is the first hint of the multi-agent question in your mission; a later lesson covers when it pays off.

For a makerspace question, most runs are short, four or five calls. Your first and cheapest levers are simpler: keep tool results small (return three relevant paragraphs, not a whole manual) and keep the system prompt tight.

Between sessions: nothing, unless you save it 6 min

If the model forgets between calls, it certainly forgets between sessions. A student trains on the laser cutter on Monday and comes back on Friday. Friday's conversation starts with a fresh context: a system prompt, tool descriptions and the new question. Unless your program does something, the assistant has no idea the student was ever trained.

The fix is memory in the practical sense used by agent builders: information the program stores outside the context window and loads back in when it is useful. Anthropic's description of structured note-taking is exactly this: the agent writes notes persisted outside the context window, which are pulled back in at later times (source). Python-wise, it is a file or database that your code reads and writes; the model never touches it directly.

For the makerspace, a student's record might look like this, a small dictionary saved as JSON:

{
  "student_id": "s1042",
  "trained_on": {"laser_cutter": "2026-10-06", "3d_printer": "2026-09-22"},
  "notes": "Prefers morning slots. Asked twice about cutting acrylic."
}

Note what is not in there: the conversation transcript. A good memory holds the few facts that will matter next time, not everything that was said. Deciding what is worth saving, and when to correct or delete it (a student's training can expire), is a design choice you make, and it matters for privacy too.

A common mix-up

"A bigger context window is a bigger memory, so with a big enough window the assistant would remember students." The window only lasts for one call or one session; closing the conversation empties it. A bigger window would hold more within a session at a higher cost. Remembering across sessions needs storage outside the window.

Retrieval: finding the right page 6 min

The other half of your mission is answering from long manuals. Suppose the manuals are too big to put in every request, or even if they fit, putting them there makes every call expensive and, by the context-rot idea above, harder for the model to use well. Anthropic's rule of thumb: if a knowledge base is smaller than about 200,000 tokens (roughly 500 pages), you can simply include it all in the prompt, with prompt caching making that cheaper; beyond that you need retrieval (Anthropic, Contextual Retrieval). Measure your manuals before you decide; many small teams find they fall on the "just include it" side, and that is a legitimate answer for a design review.

Retrieval means fetching only the pieces relevant to the question and putting those in the context. The common pattern is called retrieval-augmented generation, or RAG:

  1. Split each manual into chunks, passages of a few hundred tokens.
  2. Index the chunks so they can be searched.
  3. At question time, search with the student's question, take the top few chunks, and place them in the context for the model to answer from.

In an agent, step 3 is a tool: search_manuals(query) returns a few chunks as its result. Anthropic notes that agents increasingly work this "just in time": rather than loading data up front, they keep lightweight references such as file paths or stored queries and load the data into context at runtime using tools (source).

Two ways to search the chunks

Per Anthropic's description, the two usual indexes are embeddings, which are lists of numbers that capture the meaning of a text so that passages about similar things sit close together, and BM25, a classic keyword ranking that finds exact words and strings (source).

Student asksPage saysWhich search finds it
"Can I cut vinyl stickers on the laser?""Never cut PVC or other chlorine-containing plastics."Embeddings: the words differ, the meaning is close.
"What does fault code H-12 on the CNC mean?""H-12: spindle overheat."Keyword search: the exact code is the signal.

Combining both, and then re-ranking the results, performed best in Anthropic's tests: it cut failures to find the right chunk by 67% over plain embeddings, in their dataset (source). Treat the number as evidence that mixing methods helps, not as a promise for your manuals.

A chunk can lose its setting. A chunk that says "set the power to 40%" does not say for which machine. Anthropic's fix, contextual retrieval, adds a short note about the source document to each chunk before indexing. A simpler version you can do by hand: start every chunk with the machine name and section title.
A common mix-up

"Retrieval gives the model the manuals, so it will now know them." Retrieval gives the model a few chunks for this one call. If the search misses the right page, the model either says it does not know or, worse, answers confidently from its general training. Retrieval quality is a part of your assistant you should test with real student questions.

Worked example and practice 5 min

Worked example: where does each fact live?

For each fact the assistant needs, choose where it should live: in the context (every call), saved notes (loaded when the student returns), or retrieval (searched when asked).

  1. "Never book a machine for an untrained student." This rule applies to every request and is short. It goes in the system prompt, so in the context on every call.
  2. "The laser cutter's lens-cleaning procedure." It is long, belongs to a manual and is needed only for some questions. It goes in retrieval, fetched when asked.
  3. "This student finished 3D-printer training on 22 September." It belongs to one person and must outlast the session. It goes in saved notes, looked up when this student comes back.
  4. "The result of today's calendar lookup." It is needed for this request only. It stays in the context during the run and is not saved.

The test in each case: does it apply to every request (context), to one person across visits (notes), or to some questions out of a large collection (retrieval)?

Worked example: the cost of a big tool result

Use the earlier numbers, but suppose search_manuals returns a whole 40,000-token manual instead of three paragraphs.

  1. Calls 1 and 2 are unchanged: 2,050 and 2,400.
  2. Call 3 adds the request (50) and the manual (40,000): 2,400 + 50 + 40,000 = 42,450.
  3. Call 4 adds the request (50) and the training record (200): 42,450 + 50 + 200 = 42,700.
  4. Total input: 2,050 + 2,400 + 42,450 + 42,700 = 89,600 tokens, against 12,600 before.

One careless tool result multiplied the input by seven, and the manual was read twice for a question that needed one paragraph.

Call 2 adds the request (50) and the calendar result (300) to call 1's input: 2,200 + 50 + 300 = 2,550. Total input = 2,200 + 2,550 = 4,750 tokens.

With a lookup tool, the record would add a model call and enter the context only from that point, so a question that never needs it (a calendar-only question) would save those 150 tokens on every call. For a fact needed on almost every request, loading it up front is simpler and costs the same. Whether the record is needed on most requests is the deciding question.

Summary 2 min

  • The context is everything the model reads and writes in one call: instructions, tool descriptions, history, tool results. It has a size limit, costs money per token, and a fuller context is not always a better one.
  • Between steps, the model keeps nothing: the program re-sends the growing history on every call, so big tool results are paid for again and again.
  • Between sessions, nothing survives unless the program saves it outside the window (notes) and loads it back.
  • Retrieval brings only the relevant chunks of a large collection into the context, by meaning (embeddings), by exact words (keywords) or both.
