Context and memory in an agent

By the end of this lesson you can say, for any piece of information in the makerspace assistant, whether it lives in the model's context, in a saved note, or in a manual to be retrieved, and why.

Objective O3: context and memory in an agent About 30 minutes Builds on the agent loop (learning record 0002)
Why this matters for you

Your assistant must answer from long machine manuals and remember each student's training status between visits, all on a small budget. Every one of those needs is a context-and-memory decision, and it is the kind of decision your design review will ask you to defend.

Warm-up 2 min

Recall

From memory: in the agent loop, who runs a tool, the model or the program around it? And what happens to the tool's result?

Check your answer

The program runs the tool. The model only writes a request that names the tool and its arguments. The program then sends the result back to the model as part of its next input, and the model is called again. That last part is today's topic: "sent back as part of the next input" means the result lands in the model's context.

The context window 5 min

Start with a concrete case. A student types: "Is the laser cutter free Friday afternoon?" Your program has to call the model. What exactly does it send?

It sends a block of text with several parts: your instructions to the assistant (the system prompt), the descriptions of your tools, and the student's question. The model reads all of that and writes a reply. Nothing else reaches it. The model does not look at your booking system, your files or yesterday's chats unless the program puts their text into that block.

That block is the context: the set of tokens included when the model generates a response (Anthropic, Effective context engineering). A token is a small piece of text, roughly a short word or part of a word. The context window is the limit on how much the model can reference when it responds, including the response itself. The API documentation calls it a kind of "working memory" for the model, and says it is different from the large body of text the model was trained on (Claude docs, Context windows).

Everything in the request counts toward the window: the system prompt, every message including tool results, and the tool definitions. The reply counts too (same source).

Windows are large now: the Claude docs list up to 1 million tokens for current models (same docs page). That is why the interesting question has moved from "will it fit?" to "what should be in there?"
A common mix-up

"The model remembers things, so the window is just its memory." It is tempting because chatbots seem to remember. But the window is only the text sent this time. The model does not learn from your conversations, and it keeps nothing between calls. What feels like memory is the program re-sending earlier text. Hold on to this: the model itself is stateless; your program supplies the state.

Check yourself

The assistant answered a student correctly this morning. A different student asks a related question this afternoon, and your program sends only the new question plus the usual system prompt and tools. What does the model know about the morning?

Show the answer

Nothing. The window holds only what the program sent in this request. The morning chat is not in it, so the model cannot use it.

What is kept between steps 6 min

Inside one request, the agent loop takes several steps. Does the model "keep" anything from step to step? Same answer as before: no. The program keeps a growing list of messages and sends the whole list on every call. The docs describe this directly: each turn's input contains all previous conversation history plus the new message, and the model's output becomes part of the next input (Claude docs, Context windows).

Here is the laser cutter question as a loop, with made-up but realistic sizes. The system prompt and tool descriptions together take 1,500 tokens, and the question takes 100.

CallWhat is addedTokens sent in
1System prompt, tools, question1,600
2Model's request (50) + calendar result (400)2,050
3Model's request (50) + manual page (3,000)5,100
4Model's request (50) + training record (200)5,350

Add the last column: 1,600 + 2,050 + 5,100 + 5,350 = 14,100 input tokens for one student question, even though only about 5,350 tokens of text exist by the end. Each step re-sends everything before it. Providers bill by tokens, so this is the first reason context matters for your budget: cost grows with every step, and one large tool result is paid for again on every later call.

Prompt caching can make the repeated part cheaper to pay for, but the docs are explicit that cached tokens still occupy the window: caching changes what you pay, not whether they count (Claude docs).

Size is not the only cost. Models have what Anthropic calls an "attention budget": as the number of tokens grows, accuracy and recall degrade, an effect named context rot (Anthropic; the docs say the same and add that curating what is in context is as important as how much space is available). The goal, in Anthropic's phrase, is the smallest set of high-signal tokens that gets the result you want.

A common mix-up

"A bigger window means I can just put everything in." It is tempting because it feels safe: if the whole manual is there, nothing can be missed. But you pay for every token on every call, and a crowded context makes the model less reliable at finding the relevant line. In the table above, the 3,000-token manual page is 56% of the final context, and one question needed only a paragraph from it.

Check yourself

The assistant's third tool result is a 3,000-token manual page, and two more steps follow. Roughly how many times is that page's text sent to the model in total?

Show the answer

Three times. The page enters the input of the next call and stays in the list, so it is re-sent on each later call until something removes it.

When the context fills up 4 min

If something grows every step, you need ways to shrink it. Three common ones are worth knowing by name.

  • Clearing old tool results. Once the model has used a big result, delete its text from the list (keep a short stub). The Claude docs call this tool result clearing, a form of context editing (Claude docs).
  • Compaction. When the conversation nears the limit, summarize it and continue with the summary in a fresh window. Anthropic advises keeping critical decisions and unresolved issues and discarding redundant tool output (Anthropic).
  • Sub-agents. A separate agent does a messy job in its own context and returns only a short summary, often 1,000 to 2,000 tokens (same source). You will meet this properly in the multi-agent lesson; for now, just notice that it is another way to keep a context small.

All three are lossy: whatever is cleared or summarized away can no longer be used. So the rule is to clear what the model has finished with (a raw calendar listing after it has read Friday's slot) and keep what it still needs (the student's request and the rules).

For your assistant, most requests are short, 3 to 5 steps, so you will rarely need compaction. The cheaper win is to stop large results from entering at all. That is the retrieval section below.

Check yourself

Which of these is the safest thing to clear from the context after the assistant has used it?

Show the answer

The long raw calendar listing. It was needed once, and the conclusion drawn from it can stay. The rules and the question are needed at every step.

What is kept between sessions: notes 6 min

A session here means one conversation with one student. Everything above lived inside one request or one session. When the student closes the chat, the list of messages is gone, unless your program saved it. A new session starts with an empty window.

Your mission needs more: "remember each student's training status between visits." Picture Dana, who finished laser cutter training last Tuesday. Next week Dana asks to book it. Without saved information, the assistant would have to ask Dana again, or re-check a record every time. With it, the assistant starts knowing.

The standard answer is memory as notes: information written to storage outside the context window, and read back into context when needed. Anthropic describes this as structured note-taking, where the agent writes notes persisted outside the window and pulls them back later. In their example, an agent playing a game tracked progress such as "gained 8 levels toward the target of 10" across thousands of steps and many context resets (Anthropic).

Here is how Claude's memory tool does it, because it shows the mechanism plainly. The model can ask to view, create, edit or delete files in a /memories folder. Crucially, the tool is client-side: "Claude requests file operations, and your application runs them" against storage you control (Claude docs, Memory tool). It is the agent loop you already know, with a file as the tool. When it is enabled, the model checks its memory directory before starting a task (same source).

Model  -> tool call: memory view /memories/dana.txt
Program-> reads the file from YOUR storage, returns its text
Model  -> "Dana passed laser training on 2026-10-27"  (now in context)
...
Model  -> tool call: memory create /memories/dana.txt  (after a new training)
Program-> writes the file

Two design choices follow, both yours as the designer:

  • What to save. Save small facts that will matter later and are costly to rediscover: Dana's training status and date, a note that a booking was made. Do not save raw tool output or whole manual pages. Notes you read every session are context cost every session.
  • Who owns the truth. The training status might also live in an official record. If notes and the record disagree, the record should win. A note is a convenience, and it can go stale (the docs also suggest expiring old memory files).

For a small assistant like yours, a plain database table keyed by student ID, read by your program at the start of a session and put into the system prompt, is a perfectly good form of memory, with no model-controlled memory tool needed. That is a "fixed workflow" choice, and you will weigh it against letting the model decide in a later lesson.

A common mix-up

"Turn on memory and the assistant will automatically remember its users." It is tempting because chat apps advertise memory. But memory is something you build: storage you own, a rule for what gets written, and a step that loads it into context. Nothing is saved unless your program saves it.

Check yourself

Next week the assistant must know that Dana finished training. In the memory-tool design, which statement is true?

Show the answer

The first one: the model requests, the program executes against storage you control. Nothing else carries the fact across sessions.

Retrieval: finding the right page 5 min

The third need in your mission is finding the right place in a long manual. Say the laser cutter manual is 200 pages, about 100,000 tokens. Putting all of it into every request would cost 100,000 tokens a call, with context rot on top.

Retrieval means fetching only the relevant pieces of a large body of text and putting just those into the context. In a manual that means: split it into sections ahead of time, and at question time pick the few sections that match the student's question. There are two common ways to do this, and Anthropic names both:

  • Up front (pre-inference) retrieval. Your program searches, for instance by embedding similarity, before the model is called, and puts the top results into the first request.
  • Just-in-time retrieval. The assistant keeps lightweight handles, like section titles or file paths, and loads the content by a tool call when it decides it needs it (Anthropic).

Just-in-time fits the loop you already know: a search_manuals(machine, query) tool returns the best three sections, each trimmed to a few hundred tokens, plus their page numbers. The description you write for that tool is what lets the model call it with a good query.

An embedding is a list of numbers that places a piece of text near other texts with similar meaning; search then finds the sections nearest the question. You do not need the math (it is out of scope in your mission), only the idea: it finds "similar meaning", where keyword search finds "same words".

Retrieval is also memory of a kind, a different kind from notes. Notes hold what happened (Dana's training). Retrieval holds reference material (the manual) that no one session wrote. The table sums up the three places information can live.

WhereWhat goes thereLastsCost
ContextRules, the current question, results in useOne runPaid every call
NotesFacts about a student or past actionsAcross sessionsOnly when loaded
Retrieval storeManuals, policiesUntil you update themOnly the sections fetched
A common mix-up

"The model knows the manual because it is smart." It does not: the training text did not include your makerspace's machines. Without retrieval it will answer from general patterns and can sound sure while being wrong, much like the outdated confident chatbot answers you have already noticed. Put the right section into context and ask it to answer from that text.

Check yourself

A student asks, "What speed do I use to cut 3 mm acrylic on the laser?" Which design best fits what you have just learned?

Show the answer

Search the manual and put the top sections into context. That gets answers from the real text for the cost of a few hundred tokens.

Worked example and practice 5 min

Worked example

Dana returns and asks: "Can I use the 3D printer? Also, what filament does it take?" Decide where each piece of information lives.

  1. List every fact the answer needs. Dana's training status for the 3D printer; whether the printer is free (not needed for this question); what filament it takes; the assistant's rules.
  2. Rules go in the system prompt. They are needed at every call and they are short. This is context, and the cost is small and fixed.
  3. Dana's training status goes in notes. It is a small fact about one student, true across sessions, and not found in any manual. The program loads Dana's note at session start, so it is in context from the first call.
  4. Filament goes in retrieval. It lives in the manual. The assistant calls search_manuals("3d printer", "filament") and gets back, say, 400 tokens of text.
  5. Check the size. Context at the final call: about 1,500 (rules and tools) + 100 (question) + 60 (Dana's note) + 400 (manual) + a few small requests, roughly 2,200 tokens instead of 100,000+.
Your turn

Using the same method, place these four items. The first is done for you: "The assistant must never book a machine for an untrained student" belongs in the system prompt. Now place: (a) the fact that Dana booked the laser cutter on Friday 3 pm; (b) the maximum thickness the laser can cut; (c) the 40-line raw calendar listing the model read to find a free slot. For each, say context, notes or retrieval, and say whether it should be removed from the context afterward.

Show a solution

(a) Notes, if you want to remember it after the session. Within the session it sits in context as the booking tool's result, a short one. (b) Retrieval: it is manual content, found by search_manuals, kept in context only as long as it is needed. (c) Context only, and clear it afterward, since the model has taken what it needs from it (Friday 3 pm is free) and the raw listing is a large result that would be re-sent on every later call. Never save it as a note.

Summary 2 min

  • The model is stateless. Its context window holds only the text sent in this request, and your program supplies all state.
  • Within a run, the program re-sends the growing message list on every call, so cost and context rot rise with each step. Keep context small and clear what is finished.
  • Between sessions, nothing survives unless it is saved. Notes are facts written to storage you own and read back into context when needed.
  • Retrieval fetches only the relevant sections of a large text, so the manual stays outside the window until a question needs a piece.
