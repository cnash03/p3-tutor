Context and memory in an agent

By the end of this lesson you can decide, for each piece of information in the makerspace assistant, whether it belongs in the context window, in saved notes, or in a document store that the assistant searches.

Objective O3: context, memory and retrieval About 30 minutes Builds on the agent loop (objective O1)
Why this matters for you

Your assistant must answer from long machine manuals, remember each student's training status between visits, and stay inside a small model budget. All three are context-and-memory decisions, and you will have to defend them at your design review.

Warm-up 2 min

Before new material, pull something from the last session out of your head.

Recall

In the agent loop, who actually runs a tool such as check_calendar: the model or the program around it? And what does the program do with the result?

Check your answer

The program runs the tool. The model only writes a request that names the tool and its arguments. The program then puts the result back in front of the model and calls it again. That last part is today's topic: what exactly is in front of the model each time it is called.

The context window 5 min

A concrete case first

A student types: “Is the laser cutter free Friday afternoon?” Your program calls the model. What does the model receive? Not just those eight words. It receives one long block of text made of several parts:

  • the system prompt: your instructions (“You are the makerspace assistant. Never book a machine for an untrained student.”);
  • the tool descriptions: the names, purposes and arguments of check_calendar and the other tools;
  • the conversation so far: the student's messages, the model's earlier replies, and any tool requests and results;
  • the new student message.

All of that, together, is the context: every piece of text the model can see when it writes its next output. The model has no other view of the world. If something is not in the context, the model cannot use it, however true or important it is.

The context window is the limit on how much text the context can hold. Models read text in chunks called tokens (roughly word pieces; a short common word is usually one token, a long or rare one is several). The window is measured in tokens, and it covers the input and the model's output together.

A common mix-up

“The model remembers me.” A chatbot feels like it remembers, so it is tempting to think the model stores the conversation inside itself. It does not. After a model call finishes, the model keeps nothing from it. What feels like memory is the program sending the earlier messages again inside the next context. If the program stops sending them, the model has no idea they existed.

Check yourself

Your system prompt says “Training on the bandsaw requires a safety sign-off.” Midway through a chat, the program rebuilds the context but leaves the system prompt out by mistake. What happens on the next model call?

Show the answer

The third option. The model sees only the context it is given on each call, so a rule left out of the context is not known to it.

What is kept between steps 5 min

Now connect this to the loop. Every pass around the agent loop is a separate model call, so every pass needs a full context. The program keeps a list of everything that has happened, called the message history, and sends the whole list each time.

Take the request “Is the laser cutter free tomorrow at 3 pm, and do I need training?” Here is what the program sends on each call:

CallContext containsModel outputs
1System prompt, tool descriptions, questionRequest: check_calendar
2All of call 1, plus the request and the calendar resultRequest: check_training_record
3All of call 2, plus the request and the training resultFinal answer

Two things follow, and the second matters for your budget.

First, the memory between steps is the message history. The model “knows” the calendar result on call 2 only because the program pasted it into the context. That is the whole mechanism.

Second, the context grows with every step, and you pay for it every time. Model usage is typically billed by tokens read and tokens written, so a call with a bigger context costs more, and the early material is re-sent and re-read on every later call. Exact prices, and discounts for re-sent text, vary by provider and change over time, so check your provider's current price page. The shape of the cost does not change: longer histories mean more tokens per call, and more calls mean more times you pay.

A related cost trap is the tool result itself. If search_manuals returns a whole 40-page manual, all of it lands in the context and is re-sent on every later call. Good tools return the small piece that answers the question.
Check yourself

An agent makes 8 model calls to finish one request, and each tool result is about the same size. Which statement about cost is most accurate?

Show the answer

The first option. The program re-sends the growing history on each call, so each call has more tokens to read than the one before.

When the window fills up 5 min

Two limits apply to a long-running agent. The first is hard: when the context would exceed the window, the call fails or older text must be dropped. The second is softer and arrives earlier. Anthropic's engineering team describes context rot: as the amount of text in the context grows, the model's ability to recall information from it tends to get worse. They treat context as a finite resource with diminishing returns, and give the goal as finding “the smallest possible set of high-signal tokens” for the task (Effective context engineering for AI agents).

An academic study points the same way. Researchers testing models on questions over many documents found that accuracy was often highest when the relevant passage sat at the start or end of the input, and dropped when it sat in the middle, and that accuracy fell as the input grew longer (Liu et al., “Lost in the Middle”).

A common mix-up

“A bigger window means I can paste in every manual and be done.” It is tempting because a big window sounds like a big memory. But the window only says how much fits, not how well the model uses it. Pasting in everything also costs tokens on every call, and buries the one page that matters among hundreds that do not. Fit is not the same as attention.

So long runs need a way to shrink the history. The standard move is compaction: when the history gets long, ask the model to summarise it, then start a fresh context holding the system prompt, the summary and the most recent steps. Anthropic describes this as distilling a window’s contents so the agent can continue with little loss (same article). The risk is what the summary drops. A summary that says “checked the calendar” but loses “the laser cutter is booked until 4 pm” has thrown away the fact the next step needs.

Cheaper still is to keep things out of the history in the first place: trim tool results, and return short answers.

Check yourself

An agent’s history has grown long and costly. Which change keeps the most useful information per token?

Show the answer

The third option: compaction. It cuts the token count while keeping the goal and the recent detail.

What is kept between sessions: notes 6 min

Compaction helps within one run. A different problem appears when the student closes the chat and returns next week. A session is one conversation or run, from start to end. When it ends, the program’s message history is gone unless you saved it, and the model never kept anything. A new session starts with an empty context holding only your system prompt and tool descriptions.

So “memory between sessions” is something you build. The simplest version is notes: facts written to storage outside the context window, such as a file or a database row, and read back into the context when they are needed. Anthropic calls this structured note-taking, or agentic memory, where the agent keeps persistent notes outside the context window and pulls them back later (same article). The model does not remember; it reads what it wrote down.

For your assistant, one student’s notes might be a small record:

{
  "student_id": "s1042",
  "trained_on": ["laser cutter", "3D printer"],
  "pending": ["bandsaw safety sign-off"],
  "last_booking": "laser cutter, 2026-10-28"
}

There are two ways to wire this up, and they give different behaviour:

WiringHow it worksTrade-off
Load at the startThe program reads the record and puts it in the system promptAlways present, but costs tokens on every call, needed or not
Tools to read and writeTools get_student_record and update_student_record; the model calls them when neededCosts tokens only when used, but the model must decide to call them
A common mix-up

“Save the whole transcript and paste it in next time.” It sounds thorough, but transcripts are long, so you pay for them each call and meet the same context rot as before. Notes should be short, specific facts worth keeping, not a recording. Decide what is worth saving when you design the assistant.

Notes can also be wrong or out of date. If a student’s sign-off is revoked, the note must change too. For facts that live elsewhere, such as the booking calendar, call the real source rather than trusting a saved copy.

Retrieval: finding the right page 5 min

The third piece is about long documents. Your machine manuals together may run to hundreds of pages. You cannot put them all in the context, and as seen above you would not want to. Retrieval means fetching only the few passages relevant to the current question and putting those in the context. Anthropic lists retrieval, tools and memory as the three augmentations of the basic building block of an agent (Building effective agents).

Here is the idea with an everyday example. You do not read a whole textbook to answer “what is the Reynolds number?” You use the index, find the page, and read that page. A retrieval system does the same:

  1. Prepare once, ahead of time. Split each manual into small pieces called chunks (for example a section or a few paragraphs) and store them so they can be searched, with the manual name and page number attached.
  2. Search at question time. The student asks, “What feed speed for 3 mm acrylic on the laser cutter?” The search tool takes that text and returns the handful of best-matching chunks.
  3. Put the results in the context. The model reads those chunks and writes an answer, ideally citing the page.

In your assistant this is simply a tool, search_manuals(query, machine), so it fits the loop you already know. The model writes the query, the program runs the search, and the chunks come back as a tool result. Anthropic describes this style as just-in-time retrieval: the agent keeps light references and loads data into the context only when it needs it, rather than loading everything up front (same article).

How does the search find “matching” chunks? Two common ways, both outside the model itself: keyword search, which matches the words in the question to words in the chunks, and meaning-based search, which compares the sense of the question with the sense of each chunk (using numbers called embeddings). You do not need the mathematics. What you need is the design judgment: keyword search is simple and exact for part numbers and error codes like “E-14”; meaning-based search handles a question worded differently from the manual. Many systems use both. Try the simple one first and measure.

A common mix-up

“Retrieval teaches the model the manuals.” It does not change the model at all. Retrieval only places text in this call’s context. If the search returns the wrong chunk, the model either answers from that wrong chunk or from its general training, and may sound equally confident. The quality of the answer is capped by the quality of the search.

Check yourself

A student asks about error code “E-14” on the 3D printer. The meaning-based search returns chunks about general printer errors, not the E-14 page. Which first fix is most sensible?

Show the answer

The third option. An exact error code is a job for keyword matching; combine it with the meaning-based search.

Worked example and practice 6 min

You now have three places information can live. Here is a table that sums them up, followed by a worked example in which you place facts.

Worked example

Decide where each of these belongs: (A) “Never book a machine for an untrained student.” (B) The full text of the laser cutter manual. (C) “Student s1042 completed laser cutter training on 2026-10-02.”

  1. A: It is short, applies to every request, and the model needs it on every call to behave correctly. Put it in the system prompt, in the context. Cost is small and constant.
  2. B: It is long and only a few paragraphs matter for any one question. Put it in the document store and give the model search_manuals. The context then holds only the retrieved chunks.
  3. C: It is a small fact about one student, needed in later sessions. Save it as a note. Because training status is a record the program already has, a check_training_record tool that reads it only when asked may beat loading it every time.
Your turn

Place these three facts. For each, write the place and one reason. (D) “The 3D printer is booked 2–4 pm today.” (E) The assistant’s tone rule: “Answer in two or three sentences.” (F) “The student asked a minute ago about acrylic, and the laser cutter is free at 3 pm.” Start with E: it is short and applies to every call, so which place does that suggest?

Show a solution

E: system prompt, in the context, since it applies on every call and is short. F: the message history in the context, since it is this run’s recent results and the next step needs them. D: neither notes nor documents: it changes by the hour, so a saved copy would go stale. Call the booking tool when asked, and let the result enter the context for that run.

Summary 2 min

  • The model sees only the context of each call. It keeps nothing from one call to the next.
  • Memory between steps is the message history, re-sent on every call, so cost grows with each step.
  • A bigger window lets more fit but does not remove context rot; keep the context small and relevant, and compact long histories.
  • Memory between sessions is notes saved outside the window and read back in.
  • Retrieval puts only the matching chunks of a long document in the context, through a search tool.
