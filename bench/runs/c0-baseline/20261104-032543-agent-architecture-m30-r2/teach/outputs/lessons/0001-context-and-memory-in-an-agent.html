Context and memory in an agent

By the end of this lesson you can say what the model sees at each step of your makerspace assistant, what is carried between steps and between sessions, and where manuals and student notes should live.

Why this matters for you

Your design review will ask three things: what the assistant keeps in its context, what it saves between visits, and how it finds the right page in a long manual. Each answer also decides cost, because your sponsor's budget is small. This lesson gives you the vocabulary and a method to answer all three.

The program around the model runs the tool. It then puts the result into the next input and calls the model again. That last part is today's topic: what exactly is in that next input, and for how long does it stay?

What the model sees: the context window 5 min

Start with a concrete case. A student types: "Is the laser cutter free tomorrow at 3 pm, and do I need training to use it?"

You might picture the model "knowing" the makerspace. It does not. When your program calls the model, the model sees only the text the program sends in that one call. Nothing else exists for it: not yesterday's chats, not your booking system, not the manual on your server. Whatever is not in that text, the model cannot use.

That text is the context, and the maximum amount of text a model can handle in one call is the context window. The Claude documentation calls it the model's "working memory" and says it includes the response the model is writing as well (Claude Platform Docs, Context windows). Text is counted in tokens, the small pieces a model reads and writes, roughly a short word or part of a longer one.

For your assistant, one call contains these parts:

The docs say it plainly: "Everything in the request counts toward the context window: the system prompt, every message in messages (including tool results, images, and documents), and your tool definitions." The output counts too (Context windows). So the tool descriptions you will write for your team are not free: they are in the window on every call.

Current Claude models list windows up to 1 million tokens, depending on the model. That is a lot of manuals, but the next two sections show why "it fits" is not the same as "it is a good idea".

Between steps: the history is sent again 6 min

Now watch what happens across the steps of one request. Each step is a separate model call, and a call starts with nothing in the model's head. So how does the model know, at step 3, what happened at step 1?

Because the program sends it all again. After every tool result, the program builds the next call from the earlier messages plus the new ones. The Claude docs describe it this way: each turn's input holds "all previous conversation history plus the current user message", and the reply "becomes part of the input for the next turn" (Context windows). The model remembers nothing between calls by itself; the program is the memory, and it is the program that decides what gets sent.

Add the last column: 1,530 + 1,780 + 3,630 + 3,780 = 10,720 input tokens for one student question, although the final context is only 3,780. Each call is sent, and processed, as a whole. The docs note that on models that keep earlier thinking blocks, those "are billed as input tokens, like the rest of the conversation history", which is the same principle: history you keep is history you pay for again at each call. (Prompt caching can lower the price of a repeated beginning, but the docs are clear it "changes what you pay for those tokens, not whether they count" toward the window; see Context windows.)

That is the answer to the question from your notes about why the context window affects cost: a long tool result is paid for again on every later step of the request.

A common mix-up

"The model keeps working memory of the earlier steps, so only the new result needs to be sent." This is tempting because chat apps feel continuous. But the model is called afresh each step. If your program forgets to include the step-1 result in the step-3 call, the model genuinely does not know it happened, and may ask for the calendar again. The continuity is built by your program, which means you control it, and you pay for it.

When the window fills or rots 5 min

Two separate problems appear as the history grows.

It can run out. If the input alone exceeds the window, the API returns an error (a 400 "prompt is too long"), as the docs state (Context windows). A makerspace question rarely gets there, but one careless tool that returns a whole 200-page manual might.

It can get worse before it runs out. Anthropic's engineers call this context rot: "as the number of tokens in the context window increases, the model's ability to accurately recall information from that context decreases." They treat context as "a precious, finite resource" (Effective context engineering for AI agents). The Claude docs agree: more context "isn't automatically better."

A common mix-up

"A bigger window means the assistant remembers more, so we should just pay for the biggest one and paste in everything." A window is the size of one call, not a store that lasts. When the call ends, it is gone. And stuffing it full costs money on every call and makes the model worse at finding the one relevant sentence.

So agents trim. Three tools, from simplest to heaviest:

  • Keep results small. Make the tool return what is needed: the three relevant paragraphs, not the chapter.
  • Clear old tool results. After the model has used the calendar rows, they can be dropped from later calls. The Claude docs list "tool result clearing" among their context-editing strategies.
  • Compact. Anthropic describes compaction as "taking a conversation nearing the context window limit, summarizing its contents, and reinitiating a new context window with the summary." You lose detail, so the summary must keep decisions and open problems and can drop repeated tool output.

For a makerspace assistant, most requests are short, so the first tool does nearly all the work, and compaction matters only if a student chats for a long time.

Between sessions: nothing is kept unless you save it 6 min

Everything so far lived inside one request or one conversation. Now the student leaves, and comes back next week. In a new session the program starts with an empty history. The assistant does not know the student passed laser cutter training, unless something you built tells it.

The memory it needs has to be kept outside the context, in a place that survives: a file, a database. Then it is brought back into the context when relevant. LangGraph's docs use two names for this split. Short-term memory is the message history of one conversation (a thread). Long-term memory is stored "across multiple conversations" and can be recalled in any later thread (LangChain, Memory concepts).

Anthropic describes the model-driven version as structured note-taking: the agent writes "notes persisted to memory outside of the context window" and reads them back later (Effective context engineering). In practice, notes are just another tool: save_note(student_id, text) and read_notes(student_id). That fits the loop you already know.

What kind of thing are you saving?

The LangChain docs separate three kinds. They help you decide where each fact lives:

KindMeaningMakerspace example
SemanticFacts about the user or world"Passed laser training on 3 Nov"
EpisodicPast events and how they went"Last visit, booked the printer and no-showed"
ProceduralRules for how to act"Always check training before booking"

Procedural memory is, for your assistant, mostly the system prompt that you write by hand. Semantic memory is the training record.

One design choice here is when memories are written. Writing during the conversation ("hot path") makes them available at once but adds delay; writing in the background avoids delay but they appear later (LangChain, Memory concepts).
A common mix-up

"An agent just remembers its users." It does not, unless you build it. Many chat products do have memory features, which is why this is tempting, but that is a store plus code that loads it, exactly as in Figure 3. Also, saved facts like training status are facts that must be right. Keep those in your booking or training database and let the assistant look them up with a tool, rather than letting the model write them down in its own words and trust them later.

Retrieval: finding the right page 4 min

The third thing your team has to decide is how the assistant answers from a long manual. We saw the two bad options: paste in the whole manual (expensive, and it rots), or hope the model already knows it (it does not).

The alternative is retrieval: the assistant looks things up when it needs them and only the relevant piece enters the context. Anthropic calls this "just-in-time" context: instead of loading everything in advance, agents "maintain lightweight identifiers (file paths, stored queries, web links, etc.) and use these references to dynamically load data into context at runtime using tools" (Effective context engineering).

For the manuals, a simple design is:

  1. Before the assistant runs, split each manual into short sections, called chunks, and store them with a label such as "Laser cutter, safety, ventilation".
  2. Give the model a tool, search_manuals(query), that returns the best few chunks.
  3. The model writes the query, reads the returned chunks (now in its context), and answers from them.

How the search finds chunks (keywords, or a comparison of meaning) is a design choice for a later lesson. What matters today is where the text goes: a few hundred tokens of the right chunks enter the context, not the 30,000 tokens of the manual.

The tool's description (from your earlier lesson) matters here: the model decides when to search and what to type from that description alone.

Worked example and practice 5 min

Worked example

Decide where each item lives for the assistant. Items: (A) the rule "never book a machine for someone without training", (B) the booking calendar, (C) the 40-page laser cutter manual, (D) "this student's last project was a wooden box".

  1. A is a rule that applies to every request. Rules belong in the system prompt, which is in every call. It is short, so the cost is small.
  2. B changes by the minute and must be exact. Do not put it in the context in advance, since it would be stale. Give the model check_calendar and let a result enter the context only when needed.
  3. C is large and mostly irrelevant to any one question. Chunk it, store it outside the context, and retrieve a few chunks with search_manuals.
  4. D is small, personal, and useful in later sessions. Save it as a note in the store, and read the student's notes at the start of the next session.

The pattern: always-needed and short goes in the prompt; exact and changing goes behind a tool; large goes behind retrieval; personal and lasting goes in the store.

Your turn

Place these three items the same way, and give a reason for each: (E) the shop's emergency shutdown procedure, which must be shown whenever a student mentions smoke; (F) the student's training status for the vinyl cutter; (G) the long chat from five minutes ago in this session. Start with E: is it always needed, large, exact-and-changing, or personal-and-lasting?

Show a solution

E: It is short and safety-critical, and it applies to any request, so it goes in the system prompt as a rule (or a short document the prompt always includes). Do not rely on search to find it, because a missed search in an emergency is unacceptable.

F: It is a fact that must be exact and can change when training happens, so it stays in the training database behind a tool such as check_training_record. A note written by the model would risk going out of date.

G: It is part of the current session's history, so it stays in the context for now. If the session grows long, summarize it (compaction) or clear old tool results. Only the lasting facts from it, such as a preference, need to be saved as notes.

Summary 2 min

  • The model sees only the text of the current call, its context, which has a limit (the context window) and a cost per token.
  • Between steps, the program sends the history again, so every large tool result is paid for again on each later call, and long contexts recall worse.
  • Between sessions, nothing survives unless it is saved outside the context and loaded back, as notes or database records.
  • Retrieval brings only the relevant chunk of a long manual into the context, when a tool asks for it.

Say it in your own words: without looking, explain to a teammate why the assistant needs a store for training status and a search tool for manuals, instead of one huge prompt.
